# Plan and apply COOKIE_DOMAIN per tenant site

- New `php artisan app:rollout-cookie-domain [--type=ID…] [--domain=VALUE] [--templates] [--apply] [--json]` (`RolloutCookieDomainCommand`). For Console, Firearm and Pre Case subscriptions it works out the COOKIE_DOMAIN each site needs from its own URL and lists what it would do: `add`, `fill` (empty row), `ok`, `keep` (a different value is left alone) or `skip` (no shareable parent domain). It also shows whether the site sits under the hub's domain, since only those can hand off to Super Admin and the LMS with the shared cookie.
- A dry run unless `--apply` is passed. Applying writes the subscription `EnvVariables` rows. `--domain` limits it to sites whose proposed value is the one given. The type templates only get the key with `--templates`, because a template's single value (the hub domain) is wrong for a new site on another domain. Nothing is pushed to Forge.
- New `App\Support\Sso\CookieDomain`: the registrable domain with a leading dot (`.blackwidow.org.za`, `.bvigilant.co.za`); null for IPs, local development hosts and shared hosting domains such as `on-forge.com`.
- Tests: `tests/Feature/RolloutCookieDomainCommandTest.php`.
